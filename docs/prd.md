## 1. 제품 개요

### 1.1 한 줄 정의

런치메이트는 **"오늘 뭐 먹지?"를 10초 안에 끝내 주는 결정 앱**이다. 모바일 우선 웹앱(PWA)으로, 내 위치·예산·취향을 바탕으로 인근 식당 3곳을 제안하고, 동료와는 투표로 점심·회식 장소를 정한다.

### 1.2 문제 정의

| 문제 | 현재 상황 | 런치메이트의 해결 |
| --- | --- | --- |
| 결정 피로 | 매일 같은 고민, 지도 앱에서 수십 곳을 훑어봄 | 선택지를 3개로 좁히고 이유를 한 줄로 설명 |
| 실패한 선택 | 리뷰가 광고·체험단 위주, 실제 점심 가격을 모름 | 직장인 사용자의 실제 1인 가격·짧은 피드백 |
| 합의 비용 | 단톡방에서 "아무거나" 반복, 결정까지 10분 이상 | 초대 링크 투표, 실시간 집계, 마감 시 자동 확정 |
| 회식 장소 찾기 | 인원·예산·룸 여부를 일일이 전화로 확인 | 조건 입력 → 후보 5곳 → 바로 투표 |
| 이동 | 정한 뒤 다시 지도 앱에서 검색 | 길찾기 버튼 한 번으로 네이버 지도 도보 길찾기 |

### 1.3 포지셔닝

- 맛집 **검색** 앱이 아니라 **결정** 앱이다. 검색 결과 리스트보다 "지금 고를 3장"이 핵심 화면이다.
- 추천은 광고와 분리한다. 신뢰가 핵심 자산이다 (12장 수익화 원칙 유지).

### 1.4 제품 원칙 (모든 기능 결정의 기준)

1. **10초 원칙**: 앱을 연 순간부터 식당을 고르기까지 10초 이내. 이를 늘리는 기능은 홈 화면에 넣지 않는다.
2. **3개 이하 원칙**: 한 화면에서 고를 선택지는 3개 이하 (지도·투표방 후보 목록 제외).
3. **설명 가능한 추천**: 모든 추천 카드에는 "왜 이 집인지" 한 줄 이유가 있다.
4. **한 탭 피드백**: 피드백은 한 탭으로 끝나야 한다. 가격·태그·후기는 선택 입력이다.
5. **세련된 미니멀**: 장식보다 여백, 색보다 타이포그래피. 모든 화면은 "디자인 시안 2~3개 → 선택 → 구현" 절차를 거친다 (8.1절).

## 2. 목표와 성공 지표

### 2.1 목표

| 구분 | 목표 |
| --- | --- |
| 사용자 | 점심 결정 시간을 10초 이내로 줄이고, "실패한 점심"을 줄인다 |
| 제품 | 클로즈드 베타에서 추천이 실제 방문으로 이어지는 비율과 투표 완료율을 검증한다 |
| 사업 | 첫 집중 지역(서울)에서 매일 쓰는 직장인 사용자 기반을 만든다 (수익화 3단계 전제) |

### 2.2 비목표 (MVP에서 하지 않는 것)

- 식당 정보(메뉴·사진·영업시간)를 자체 수집·저장하는 것 (카카오 저장 정책)
- 예약·결제·주문 기능
- 네이티브 앱(iOS/Android 스토어) 출시
- 광고·스폰서 노출 (수익화 1단계 = 무광고)
- AI(LLM) 기능 (3단계)
- 채팅·댓글 등 사용자 간 대화 기능

### 2.3 성공 지표 (베타 게이트 기준) [PRD 추가]

목표치는 베타 결과로 재조정한다. 측정 이벤트는 10장 참조.

| 지표 | 정의 | 베타 목표 |
| --- | --- | --- |
| **North Star: 주간 결정 수** | 주당 "길찾기 클릭 + 투표 확정 + 방문 기록" 합계 / 활성 사용자 | 사용자당 주 2회 이상 |
| 추천 수락률 | 추천 노출 세션 중 길찾기·즐겨찾기·투표 추가로 이어진 비율 | 30% 이상 |
| 결정 소요 시간 | 홈 진입 → 첫 길찾기 클릭 중앙값 | 20초 이하 (궁극 목표 10초) |
| 다시 뽑기 횟수 | 결정 세션당 평균 | 2회 이하 |
| 피드백 응답률 | 피드백 요청 노출 대비 응답 | 40% 이상 |
| 투표 완료율 | 생성된 투표방 중 확정까지 간 비율 | 60% 이상 |
| 투표 초대 전환율 | 초대 링크 열람 → 로그인 → 투표 완료 | 50% 이상 |
| 온보딩 완료율 | 첫 로그인 → 온보딩 완료 | 80% 이상 |
| W4 리텐션 | 가입 4주 뒤 주 1회 이상 사용 | 30% 이상 |

### 3.2 핵심 사용자 과업 (Jobs To Be Done)

- 점심 10분 전에, **고민 없이 갈 곳 하나를 정하고 싶다.**
- 동료들과 점심 갈 때, **단톡방 논쟁 없이 모두가 납득하는 곳을 정하고 싶다.**
- 회식을 맡았을 때, **조건에 맞는 후보를 빨리 모아 팀 의견을 받고 싶다.**
- 먹고 나서, **좋았던 곳·별로였던 곳을 기억해서 다음 선택에 반영되게 하고 싶다.**

## 4. 핵심 사용자 흐름

### 4.1 첫 사용 (비로그인 → 가입)

```
랜딩 → [추천 체험] → 위치 권한 → 둘러보기 추천 3장 (설정 저장 불가 안내)
     → [카카오/네이버/구글로 시작] → 약관 동의(필수·선택) → 온보딩 3단계 → 오늘(홈)
```

- 둘러보기에서 고른 위치·예산은 가입 후 온보딩 기본값으로 이어받는다. [PRD 추가]

### 4.2 매일 점심 (재방문 사용자, 핵심 흐름)

```
앱 열기 → (어제 방문 피드백 한 탭, 건너뛰기 가능) → 오늘 카드 3장
       → 스와이프로 비교 → [길찾기] → 네이버 지도 도보 길찾기
       → 방문 기록 후보 저장 → 다음 접속 시 피드백 요청
```

### 4.3 친구 초대 투표

```
방장: 오늘/회식 → [친구랑 정하기] → 후보 2~5곳 선택 → 제목·마감 시각 → 생성
     → 카카오톡 공유 / 링크 복사 / 공유창
참여자: 링크 열기 → 투표방 미리보기 → (인앱 브라우저면 외부 브라우저 안내)
       → 로그인 → 투표방 자동 복귀 → 투표 → 실시간 집계 확인
마감: 시각 도달 또는 방장 [결정] → 1위 확정(동점 시 방장 선택·룰렛)
     → 결과 카드 + 길찾기 → 참여자 방문 기록 후보 → 다음 접속 시 피드백
```

### 4.4 회식 모드

```
오늘 → [회식 모드] → 인원·1인 예산·룸/단체석·주류 → 후보 5곳 리스트
     → 상세에서 네이버 플레이스 확인 → [이 후보로 투표 만들기] → 4.3 흐름
```

## 6. 기능 요구사항

수용 기준(AC)은 `plan.md` 작업 완료 판단과 테스트 케이스의 기준이다.

### 6.1 인증·계정 (AUTH)

| ID | 요구사항 | 우선 | 비고 |
| --- | --- | --- | --- |
| AUTH-01 | 카카오·구글 소셜 로그인 (Supabase Auth) | P0 | [확정] |
| AUTH-01N | **네이버 로그인** (커스텀 OAuth: Vercel 서버 함수에서 네이버 인증 → 프로필 조회 → Supabase 사용자 생성·세션 발급) | P0 | [확정] 구현 방식 [확인 필요]: Supabase 커스텀 OAuth/OIDC provider 지원 여부를 먼저 확인하고, 불가하면 서버 함수 + Supabase Admin API 방식. 네이버 개발자센터 앱 등록·검수 필요 |
| AUTH-02 | 첫 로그인 시 약관 동의 화면 → 온보딩으로 연결 | P0 | |
| AUTH-03 | 로그인 후 원래 보던 경로로 복귀 (특히 `/poll/{code}`) | P0 | |
| AUTH-04 | **인앱 브라우저 감지와 외부 브라우저 열기 안내** | P0 | [PRD 추가] 아래 설명 |
| AUTH-05 | 로그아웃, 회원 탈퇴(즉시 처리 + 데이터 삭제 정책 11.4절) | P0 | |
| AUTH-06 | 만 14세 이상 확인 (약관 동의 단계 체크박스) | P0 | [PRD 추가] 개인정보보호법상 만 14세 미만은 법정대리인 동의 필요 → 가입 제한으로 단순화 |
| AUTH-07 | 비로그인 둘러보기: 추천 체험만 허용, 저장·후기·투표 시도 시 로그인 유도 시트 | P0 | |
| AUTH-08 | 같은 이메일의 카카오·네이버·구글 계정 연결(계정 통합) | P2 | 이메일 미수집 시 불가, 2단계 검토 |

**AUTH-04 배경 (빠진 요구사항)**: 투표 초대 링크는 대부분 카카오톡에서 열리고, 카카오톡 인앱 브라우저에서는 **구글 로그인이 차단된다**(구글 정책상 임베디드 웹뷰 OAuth 거부). 투표 참여가 로그인 필수이므로 대응하지 않으면 투표 전환율이 크게 떨어진다.

- 투표 참여는 **로그인 필수를 유지**한다 [확정]. 베타에서 `poll_invite_opened → poll_voted` 전환율이 50% 미만이면 게스트 투표를 재검토한다.
- 카카오톡·인스타그램·네이버 등 인앱 브라우저를 User-Agent로 감지한다.
- 인앱 브라우저에서는 **카카오 로그인을 기본 버튼**으로 크게 노출하고(네이버 로그인도 함께 노출, 인앱 동작은 실기기 확인), 구글 버튼 탭 시 "외부 브라우저에서 열기" 안내를 띄운다.
- Android 카카오톡은 외부 브라우저 열기 스킴으로 자동 전환을 시도하고, iOS는 "··· → 다른 브라우저로 열기" 안내 이미지를 보여준다. [확인 필요: 카카오톡 외부 브라우저 스킴 동작]

**AC**
- AC-AUTH-1: 카카오톡에서 `/poll/{code}` 링크를 열고 카카오 로그인하면, 로그인 후 같은 투표방 화면으로 돌아온다.
- AC-AUTH-2: 카카오톡 인앱 브라우저에서 구글 로그인 버튼을 누르면 OAuth 오류 화면이 아니라 외부 브라우저 안내가 뜬다.
- AC-AUTH-3: 탈퇴 후 같은 소셜 계정으로 다시 로그인하면 새 사용자로 시작한다(이전 설정·기록 없음).

### 6.2 온보딩 (ONB)

### 6.6A 할인·이벤트 (DEAL) [확정]

카카오·네이버 API는 쿠폰·할인·이벤트 정보를 주지 않으므로 직접 모은다. 출처를 단계적으로 늘린다.

| 출처 | 도입 | 배지 | 성격 |
| --- | --- | --- | --- |
| 사용자 제보 | MVP | `제보` | 정보 (광고 아님) |
| 사장님 무료 등록 | 2단계 | `사장님 등록` | 정보 (광고 아님, 무료) |
| 유료 제휴 쿠폰 | 3단계 (수익화 12장) | `제휴` | 광고 |

**원칙**
- 할인·이벤트 정보는 **표시만 하고 추천 점수에는 어떤 출처든 반영하지 않는다** (무료 정보 포함). 신뢰 원칙(1.3절)을 지킨다.
- 출처 배지를 항상 붙여 제보·사장님 등록·제휴를 구분한다.
- "할인 중" 필터는 MVP에 넣지 않는다 (베타에서 제보 양을 보고 재검토).

| ID | 요구사항 | 우선 |
| --- | --- | --- |
| DEAL-01 | 사용자 제보 등록: 유형(점심특선 / 할인 / 오픈·기념 이벤트 / 해피아워 / 기타), 내용 60자, 적용 요일·시간대(선택), 종료일(기본 7일, 최대 30일). 식당 상세에서 진입 | P1 |
| DEAL-02 | 표시: 추천 카드·지도 마커에 작은 `할인` 배지, 식당 상세에 유효한 정보 목록(출처 배지, 제보 시각, 종료일). "실제와 다를 수 있어요" 안내 | P1 |
| DEAL-03 | 최신성 확인: 상세에서 "아직 해요 / 끝났어요" 한 탭. "끝났어요" 3건(서로 다른 사용자) 누적 또는 종료일 경과 시 자동 숨김 | P1 |
| DEAL-04 | 남용 방지: 제보 하루 10건, 같은 식당 같은 유형 중복 제보 병합, 금칙어, 신고 사유에 "광고성·허위" 추가 | P1 |
| DEAL-05 | 투표방 후보 카드에는 `제보`·`사장님 등록` 배지 표시 가능, `제휴` 쿠폰은 표시하지 않음 (12.3절 광고 배치 규칙 유지) | P1 |
| DEAL-06 | 사장님 인증: 사업자등록번호 진위 확인 + 가게 대표 전화 또는 관리자 수동 검수로 `place_id` 소유 확인 | P2 (2단계) |
| DEAL-07 | 사장님 무료 등록: 가게 소식·할인·이벤트 등록·수정·종료, 사장님 등록 정보는 사용자 제보보다 위에 표시 | P2 (2단계) |
| DEAL-08 | 유료 제휴 쿠폰: basic-plan 12장 3단계 계획대로 (`sponsors`, `coupons`) | P2 (3단계) |

**축소안 (일정 지연 시)**: DEAL-03의 "아직 해요" 확인을 빼고 종료일 만료만 적용.

**AC**
- AC-DEAL-1: 종료일이 지난 할인 정보는 어떤 화면에도 보이지 않는다.
- AC-DEAL-2: 할인 정보가 있는 식당과 없는 식당의 추천 점수는 다른 조건이 같으면 동일하다(단위 테스트).
- AC-DEAL-3: 서로 다른 사용자 3명이 "끝났어요"를 누르면 해당 정보가 즉시 숨겨진다.

**사장님 등록을 2단계에 두는 이유**: 무료 등록으로 사장님 계정을 먼저 모아 두면, 3단계 유료 제휴 영업 때 연락할 수 있는 가게 목록이 된다. 서울 첫 영업 권역 선정(Q10)에도 쓸 수 있다.

**마감 처리 방식** [PRD 추가]: Vercel Cron은 무료(Hobby) 플랜에서 실행 빈도 제한이 있어 분 단위 마감 처리에 적합하지 않다 [확인 필요]. 다음 조합으로 처리한다.
1. **조회 시 판정**: 투표방을 읽을 때 `마감 시각 < 현재`이고 상태가 진행이면 서버 함수(또는 Postgres 함수)가 즉시 확정 처리한다.
2. **보조 스케줄러**: Supabase `pg_cron`으로 1분마다 만료 투표 확정 (아무도 접속하지 않아도 확정되도록).
3. 확정 이벤트를 Realtime으로 브로드캐스트해 열려 있는 화면을 결과 화면으로 전환한다.

**AC**
- AC-POLL-1: 2명 이상이 각자 기기에서 투표하면 상대 화면의 득표 바가 2초 안에 갱신된다.
- AC-POLL-2: 마감 시각이 지난 뒤 아무도 투표방을 열지 않았어도, 다음에 누가 열면 확정 결과가 보인다.
- AC-POLL-3: 초대 코드를 모르는 사용자는 투표방을 조회할 수 없다(RLS·추측 불가한 코드 길이 10자 이상).
- AC-POLL-4: 카카오톡 공유 미리보기에 투표 제목과 마감 시각이 보인다.

basic-plan 7장을 기준으로 한다. PRD에서 정하는 것은 **동작 규칙과 검증 기준**이고, 가중치 수치는 `plan.md`와 코드에서 상수로 관리한다.

| 규칙 | 내용 |
| --- | --- |

**검증**: 추천 함수는 입력(후보 목록·사용자 설정·피드백)에 대해 결정적(시드 고정 시)이어야 하고, 하드 필터·다양성·반복 패널티 규칙마다 단위 테스트를 둔다.

## 8. 디자인 요구사항

### 8.1 디자인 프로세스 원칙 (필수) [확정]

**모든 화면·주요 컴포넌트는 구현 전에 2~3개 시안을 먼저 만들고, 사용자가 하나를 고른 뒤에 구현한다.** Claude Code 작업에서 이 절차를 건너뛰지 않는다. `CLAUDE.md`에 규칙으로 옮긴다.

| 단계 | 내용 | 산출물 |
| --- | --- | --- |
| 1. 시안 | 같은 요구사항으로 방향이 분명히 다른 2~3안 (예: A 카드 중심 / B 리스트 중심 / C 대담한 타이포) | 정적 HTML 또는 `/design-lab/{화면}` 페이지, 390px·1280px 캡처 |
| 2. 선택 | 사용자가 1안 선택 또는 조합 지시 | 선택 결과를 `docs/design-decisions.md`에 기록 |
| 3. 구현 | 선택안을 디자인 토큰·공통 컴포넌트로 구현 | PR + Vercel 미리보기 |
| 4. 검수 | 390px 실기기, 다크 모드, 대비 4.5:1 확인 | 체크리스트 통과 |

시안 작성이 필요한 단위:
1. **디자인 시스템 (가장 먼저)**: 포인트 컬러·타이포 스케일·라운드·그림자 조합 3안
2. 랜딩
3. 오늘(홈) 추천 카드 ← 가장 중요한 화면
4. 지도 + 바텀시트
5. 투표방(진행·결과)
6. 온보딩
7. 회식 모드, 피드백 카드, 나

### 8.2 디자인 방향 [확정 + 보완]

- **톤**: 따뜻하지만 군더더기 없는 미니멀. 아이보리 배경 + 단일 포인트 컬러(토마토 레드 계열 기본안)
- **타이포**: Pretendard 단일 서체, 숫자(도보 분·가격)는 크게·`tabular-nums`
- **레이아웃**: 한 손 조작, 주요 버튼은 화면 하단 1/3, 터치 영역 44px 이상
- **모션**: 카드 스와이프, 다시 뽑기 셔플, 바텀시트 스프링, 득표 바, 확정 순간 짧은 축하 모션. `prefers-reduced-motion` 존중
- **다크 모드**: 아이보리 → 따뜻한 차콜, 포인트 컬러 채도 조정
- **컴포넌트**: shadcn/ui + Lucide, 디자인 토큰(색·간격·라운드·그림자·모션 시간) 먼저 정의
- **레퍼런스 후보** [확인 필요]: 토스(숫자·여백), Airbnb(카드), Linear(정밀함), 당근(로컬 친근함)

### 8.3 사진 없는 카드 디자인 (빠진 요구사항) [PRD 추가]

카카오 로컬 API는 **식당 사진을 제공하지 않는다**. 추천 카드가 사진 없이도 매력적이어야 한다.

- 카테고리별 **일러스트·아이콘 + 색면** 시스템 (한식·중식·일식·양식·분식·국밥·고기·카페 등 12종 내외)
- 카드 주인공은 **식당명과 숫자**(도보 4분 · 9천 원대 · 👍 87%)
- 시안 단계에서 "일러스트형 / 타이포형 / 이모지·그라데이션형" 3안 비교 권장
- 사용자 업로드 사진은 MVP에서 받지 않음 (저작권·초상권·검수 부담) → 2단계 검토

### 8.4 화면별 상태 요구사항

모든 데이터 화면은 **로딩(스켈레톤) · 빈 상태 · 오류 · 오프라인** 4가지 상태 디자인을 시안에 포함한다.

## 14. 출시 계획과 출시 기준

| 단계 | 기간(예상) | 진입 조건 | 종료 조건 |

※ 디자인 시안 작성·선택 시간, 네이버 로그인, MVP에 채택한 P1 기능 4종(그냥 골라줘, 웨이팅 제보, 기피 음식 경고, 결과 공유 이미지)을 더하면 전체 약 6.5~7주 예상. 일정이 밀리면 P1 4종은 베타 이후로 넘길 수 있다.

### 14.1 서비스 도메인 [확정]

- **개발 ~ 클로즈드 베타**: Vercel 기본 도메인(`*.vercel.app`, 예: `lunchmate.vercel.app`)을 쓴다. 0단계에서 프로젝트 이름이 비어 있는지 먼저 확인하고, 모든 외부 콘솔에는 **프로덕션 도메인**을 등록한다(PR 미리보기 도메인은 로그인 테스트용으로만 별도 등록).
- **공개 출시 전**: 자체 도메인(예: `lunchmate.kr`)을 구매해 Vercel에 연결한다. 가능하면 베타 시작 전에 연결해, 베타 참여자의 PWA 재설치와 초대 링크 단절을 피한다.
- **도메인 전환 체크리스트**
  - [ ] Vercel: 자체 도메인 연결, `*.vercel.app` → 자체 도메인 301 리다이렉트 (기존 투표 초대 링크 유지)
  - [ ] 카카오: 플랫폼 Web 사이트 도메인(JS 키·공유), 카카오 로그인 Redirect URI
  - [ ] 네이버: 지도 Client ID 서비스 URL, 네이버 로그인 서비스 URL·Callback URL (검수 재요청 여부 확인)
  - [ ] 구글 Cloud Console: OAuth 승인된 JavaScript 원본·리디렉션 URI
  - [ ] Supabase: Site URL, Redirect URLs
  - [ ] 네이버 지도 URL Scheme `appname` 값
  - [ ] OG 이미지·메타 태그·매니페스트의 절대 URL, PostHog·Sentry 도메인 설정
  - [ ] 환경변수(`NEXT_PUBLIC_SITE_URL` 등) 갱신 후 재배포, 실기기에서 로그인 3종·공유·길찾기 재확인
  - [ ] 베타 참여자에게 PWA 재설치 안내 (베타 중 전환한 경우)

### 14.2 공개 출시 체크리스트

- [ ] 자체 도메인 연결과 14.1절 전환 체크리스트 완료
