## 1. 제품 개요

### 1.1 한 줄 정의

런치메이트는 **"오늘 뭐 먹지?"를 10초 안에 끝내 주는 결정 앱**이다. 모바일 우선 웹앱(PWA)으로, 내 위치·예산·취향을 바탕으로 인근 식당 3곳을 제안하고, 동료와는 투표로 점심·회식 장소를 정한다.

### 1.2 문제 정의

| 문제 | 현재 상황 | 런치메이트의 해결 |
| --- | --- | --- |
| 결정 피로 | 매일 같은 고민, 지도 앱에서 수십 곳을 훑어봄 | 선택지를 3개로 좁히고 이유를 한 줄로 설명 |
| 실패한 선택 | 리뷰가 광고·체험단 위주, 실제 점심 가격을 모름 | 직장인 사용자의 실제 1인 가격·짧은 피드백 |
| 합의 비용 | 단톡방에서 "아무거나" 반복, 결정까지 10분 이상 | 초대 링크 투표, 실시간 집계, 마감 시 자동 확정 |
| 회식 장소 찾기 | 인원·예산·룸 여부를 일일이 전화로 확인 | 조건 입력 → 후보 5곳 → 바로 투표 |
| 이동 | 정한 뒤 다시 지도 앱에서 검색 | 길찾기 버튼 한 번으로 네이버 지도 도보 길찾기 |

### 1.3 포지셔닝

- 맛집 **검색** 앱이 아니라 **결정** 앱이다. 검색 결과 리스트보다 "지금 고를 3장"이 핵심 화면이다.
- 추천은 광고와 분리한다. 신뢰가 핵심 자산이다 (basic-plan 12장 수익화 원칙 유지).

### 1.4 제품 원칙 (모든 기능 결정의 기준)

1. **10초 원칙**: 앱을 연 순간부터 식당을 고르기까지 10초 이내. 이를 늘리는 기능은 홈 화면에 넣지 않는다.
2. **3개 이하 원칙**: 한 화면에서 고를 선택지는 3개 이하 (지도·투표방 후보·회식 후보 목록 제외).
3. **설명 가능한 추천**: 모든 추천 카드에는 "왜 이 집인지" 한 줄 이유가 있다.
4. **한 탭 피드백**: 피드백은 한 탭으로 끝나야 한다. 가격·태그·후기는 선택 입력이다.
5. **세련된 미니멀**: 장식보다 여백, 정보 위계는 타이포그래피로. 모든 화면은 "디자인 시안 3안 이상 → 선택 → 구현" 절차를 거친다 (8.1절).

## 2. 목표와 성공 지표

### 2.1 목표

| 구분 | 목표 |
| --- | --- |
| 사용자 | 점심 결정 시간을 10초 이내로 줄이고, "실패한 점심"을 줄인다 |
| 제품 | 클로즈드 베타에서 추천이 실제 방문으로 이어지는 비율과 투표 완료율을 검증한다 |
| 사업 | 첫 집중 지역(서울)에서 매일 쓰는 직장인 사용자 기반을 만든다 (수익화 3단계의 전제) |

### 2.2 비목표 (MVP에서 하지 않는 것)

- 식당 정보(메뉴·사진·영업시간)를 자체 수집·저장하는 것 (카카오 저장 정책)
- 예약·결제·주문 기능
- 네이티브 앱(iOS/Android 스토어) 출시
- 광고·스폰서 노출 (수익화 1단계 = 무광고)
- AI(LLM) 기능 (3단계)
- 채팅·댓글 등 사용자 간 대화 기능

### 2.3 성공 지표 (베타 게이트 기준) [PRD 추가]

목표치는 베타 결과로 재조정한다. 측정 이벤트는 10장 참조.

| 지표 | 정의 | 베타 목표 |
| --- | --- | --- |
| **North Star: 주간 결정 수** | 주당 "길찾기 클릭 + 투표 확정 + 방문 기록" 합계 / 활성 사용자 | 사용자당 주 2회 이상 |
| 추천 수락률 | 추천 노출 세션 중 길찾기·즐겨찾기·투표 추가로 이어진 비율 | 30% 이상 |
| 결정 소요 시간 | 홈 진입 → 첫 길찾기 클릭 중앙값 | 20초 이하 (궁극 목표 10초) |
| 다시 뽑기 횟수 | 결정 세션당 평균 | 2회 이하 |
| 피드백 응답률 | 피드백 요청 노출 대비 응답 | 40% 이상 |
| 투표 완료율 | 생성된 투표방 중 확정까지 간 비율 | 60% 이상 |
| 투표 초대 전환율 | 초대 링크 열람 → 로그인 → 투표 완료 | 50% 이상 |
| 온보딩 완료율 | 첫 로그인 → 온보딩 완료 | 80% 이상 |
| W4 리텐션 | 가입 4주 뒤 주 1회 이상 사용 | 30% 이상 |

### 3.2 핵심 사용자 과업 (Jobs To Be Done)

- 점심 10분 전에, **고민 없이 갈 곳 하나를 정하고 싶다.**
- 동료들과 점심 갈 때, **단톡방 논쟁 없이 모두가 납득하는 곳을 정하고 싶다.**
- 회식을 맡았을 때, **조건에 맞는 후보를 빨리 모아 팀 의견을 받고 싶다.**
- 먹고 나서, **좋았던 곳·별로였던 곳을 기억해서 다음 선택에 반영되게 하고 싶다.**

### 3.3 이용 환경 [PRD 추가]

- 주 사용 기기: 스마트폰 (iOS Safari, Android Chrome), 카카오톡 인앱 브라우저(투표 초대 링크 진입 시)
- 보조: 데스크톱 Chrome·Edge·Safari (사무실 PC에서 투표방 생성)
- 사용 시간대: 평일 11:00~13:30 (점심), 17:00~19:00 (저녁·회식) 피크
- 네트워크: 실내·지하 식당가에서 약한 신호 가능 → 로딩 상태와 오프라인 기본 화면 필수

## 4. 핵심 사용자 흐름

### 4.1 첫 사용 (비로그인 → 가입)

```
랜딩 → [추천 체험] → 위치 권한 → 둘러보기 추천 3장 (설정 저장 불가 안내)
     → [카카오/네이버/구글로 시작] → 약관 동의(필수·선택) → 온보딩 3단계 → 오늘(홈)
```

- 둘러보기에서 고른 위치·예산은 가입 후 온보딩 기본값으로 이어받는다. [PRD 추가]

### 4.2 매일 점심 (재방문 사용자, 핵심 흐름)

```
앱 열기 → (어제 방문 피드백 한 탭, 건너뛰기 가능) → 오늘 카드 3장
       → 스와이프로 비교 → [길찾기] → 네이버 지도 도보 길찾기
       → 방문 기록 후보 저장 → 다음 접속 시 피드백 요청
```

### 4.3 친구 초대 투표

```
방장: 오늘/회식 → [친구랑 정하기] → 후보 2~5곳 선택 → 제목·마감 시각 → 생성
     → 카카오톡 공유 / 링크 복사 / 공유창
참여자: 링크 열기 → 투표방 미리보기 → (인앱 브라우저면 외부 브라우저 안내)
       → 로그인 → 투표방 자동 복귀 → 투표 → 실시간 집계 확인
마감: 시각 도달 또는 방장 [결정] → 1위 확정(동점 시 방장 선택·룰렛)
     → 결과 카드 + 길찾기 → 참여자 방문 기록 후보 → 다음 접속 시 피드백
```

### 4.4 회식 모드

```
오늘 → [회식 모드] → 인원·1인 예산·룸/단체석·주류 → 후보 5곳 리스트
     → 상세에서 네이버 플레이스 확인 → [이 후보로 투표 만들기] → 4.3 흐름
```

## 5. 범위

### 5.1 단계별 범위

| 단계 | 포함 |
| --- | --- |
| **MVP (클로즈드 베타 → 공개 출시)** | 로그인·온보딩·설정, 오늘의 추천, 주변 지도, 길찾기, 식후 피드백·후기, 할인·이벤트 사용자 제보, 기록, 친구 초대 투표, 회식 모드, 신고·제보, 관리자 화면, PWA, 약관·탈퇴 |
| **2단계** | 사장님 무료 등록(가게 소식·할인·이벤트), 점심 알림 푸시, 날씨 연동, 친구 목록, 우리 회사 맛집 지도(회사 이메일 인증 그룹), 월간 점심 리포트, 수익화 2단계(제한적 네이티브 배너) |
| **3단계** | AI 자연어 추천, AI 후기 요약, 협업 필터링, 프리미엄 구독 |

### 5.2 우선순위 정의

- **P0**: 없으면 출시 불가
- **P1**: MVP에 포함하되, 일정이 밀리면 범위를 줄여 출시 가능 (축소안 명시)
- **P2**: MVP 이후

## 6. 기능 요구사항

**AUTH-04 배경 (빠진 요구사항)**: 투표 초대 링크는 대부분 카카오톡에서 열리고, 카카오톡 인앱 브라우저에서는 **구글 로그인이 차단된다**(구글 정책상 임베디드 웹뷰 OAuth 거부). 투표 참여가 로그인 필수이므로 대응하지 않으면 투표 전환율이 크게 떨어진다.

- 투표 참여는 **로그인 필수를 유지**한다 [확정]. 베타에서 `poll_invite_opened → poll_voted` 전환율이 50% 미만이면 게스트 투표를 재검토한다.
- 카카오톡·인스타그램·네이버 등 인앱 브라우저를 User-Agent로 감지한다.
- 인앱 브라우저에서는 **카카오 로그인을 기본 버튼**으로 크게 노출하고(네이버 로그인도 함께 노출, 인앱 동작은 실기기 확인), 구글 버튼 탭 시 "외부 브라우저에서 열기" 안내를 띄운다.
- Android 카카오톡은 외부 브라우저 열기 스킴으로 자동 전환을 시도하고, iOS는 "··· → 다른 브라우저로 열기" 안내 이미지를 보여준다. [확인 필요: 카카오톡 외부 브라우저 스킴 동작]

**AC**
- AC-AUTH-1: 카카오톡에서 `/poll/{code}` 링크를 열고 카카오 로그인하면, 로그인 후 같은 투표방 화면으로 돌아온다.
- AC-AUTH-2: 카카오톡 인앱 브라우저에서 구글 로그인 버튼을 누르면 OAuth 오류 화면이 아니라 외부 브라우저 안내가 뜬다.
- AC-AUTH-3: 탈퇴 후 같은 소셜 계정으로 다시 로그인하면 새 사용자로 시작한다(이전 설정·기록 없음).

### 6.6A 할인·이벤트 (DEAL) [확정]

카카오·네이버 API는 쿠폰·할인·이벤트 정보를 주지 않으므로 직접 모은다. 출처를 단계적으로 늘린다.

| 출처 | 도입 | 배지 | 성격 |
| --- | --- | --- | --- |
| 사용자 제보 | MVP | `제보` | 정보 (광고 아님) |
| 사장님 무료 등록 | 2단계 | `사장님 등록` | 정보 (광고 아님, 무료) |
| 유료 제휴 쿠폰 | 수익화 3단계 (basic-plan 12장) | `제휴` | 광고 |

**원칙**
- 할인·이벤트 정보는 **표시만 하고 추천 점수에는 어떤 출처든 반영하지 않는다** (무료 정보 포함). 신뢰 원칙(1.3절)을 지킨다.
- 출처 배지를 항상 붙여 제보·사장님 등록·제휴를 구분한다.
- "할인 중" 필터는 MVP에 넣지 않는다 (베타에서 제보 양을 보고 재검토).

| ID | 요구사항 | 우선 |
| --- | --- | --- |
| DEAL-01 | 사용자 제보 등록: 유형(점심특선 / 할인 / 오픈·기념 이벤트 / 해피아워 / 기타), 내용 60자, 적용 요일·시간대(선택), 종료일(기본 7일, 최대 30일). 식당 상세에서 진입 | P1 |
| DEAL-02 | 표시: 추천 카드·지도 마커에 작은 `할인` 배지, 식당 상세에 유효한 정보 목록(출처 배지, 제보 시각, 종료일). "사용자가 제보한 정보라 실제와 다를 수 있습니다." 안내 | P1 |
| DEAL-03 | 최신성 확인: 상세에서 "아직 해요 / 끝났어요" 한 탭. "끝났어요" 3건(서로 다른 사용자) 누적 또는 종료일 경과 시 자동 숨김 | P1 |
| DEAL-04 | 남용 방지: 제보 하루 10건, 같은 식당 같은 유형 중복 제보 병합, 금칙어, 신고 사유에 "광고성·허위" 추가 | P1 |
| DEAL-05 | 투표방 후보 카드에는 `제보`·`사장님 등록` 배지 표시 가능, `제휴` 쿠폰은 표시하지 않음 (basic-plan 12.3절 광고 배치 규칙 유지) | P1 |
| DEAL-06 | 사장님 인증: 사업자등록번호 진위 확인 + 가게 대표 전화 또는 관리자 수동 검수로 `place_id` 소유 확인 | P2 (제품 2단계) |
| DEAL-07 | 사장님 무료 등록: 가게 소식·할인·이벤트 등록·수정·종료, 사장님 등록 정보는 사용자 제보보다 위에 표시 | P2 (제품 2단계) |
| DEAL-08 | 유료 제휴 쿠폰: basic-plan 12장 수익화 3단계 계획대로 (`sponsors`, `coupons`) | P2 (수익화 3단계) |

**축소안 (일정 지연 시)**: DEAL-03의 "아직 해요" 확인을 빼고 종료일 만료만 적용.

**AC**
- AC-DEAL-1: 종료일이 지난 할인 정보는 어떤 화면에도 보이지 않는다.
- AC-DEAL-2: 할인 정보가 있는 식당과 없는 식당의 추천 점수는 다른 조건이 같으면 동일하다(단위 테스트).

**사장님 등록을 제품 2단계에 두는 이유**: 무료 등록으로 사장님 계정을 먼저 모아 두면, 수익화 3단계 유료 제휴 영업 때 연락할 수 있는 가게 목록이 된다. 서울 첫 영업 권역 선정(Q10)에도 쓸 수 있다.

## 8. 디자인 요구사항

### 8.1 디자인 프로세스 원칙 (필수) [확정]

**모든 화면·주요 컴포넌트는 구현 전에 3안 이상 시안을 먼저 만들고, 사용자가 하나를 고른 뒤에 구현한다.** Claude Code 작업에서 이 절차를 건너뛰지 않는다. 세부 절차와 비교표 양식은 `tasks.md` 2.3절이 정본이다.

| 단계 | 내용 | 산출물 |
| --- | --- | --- |
| 1. 시안 | 같은 요구사항으로 방향이 분명히 다른 3안 이상 (예: A 스와이프 스택 / B 피크 캐러셀 / C 세로 3단 비교) | `/design-lab/{화면}` 페이지, 390px·1280px 캡처 |
| 2. 선택 | 사용자가 1안 선택 또는 조합 지시 | 선택 결과를 `docs/design-decisions.md`에 기록 |
| 3. 구현 | 선택안을 디자인 토큰·공통 컴포넌트로 구현 | `main` 커밋·푸시(미완성은 기능 플래그) → Vercel 자동 배포 |

시안 작성이 필요한 단위 (`tasks.md` 단계 순서):
1. **디자인 시스템 (가장 먼저, G1)**: `DESIGN.md` 시안 3안을 같은 홈 화면에 입혀 비교
2. 오늘(홈) 추천 카드 ← 가장 중요한 화면, 랜딩 (G3)
3. 온보딩, 로그인 시트·약관·인앱 브라우저 안내
4. 지도 + 바텀시트, 식당 상세
5. 피드백 카드, 나·기록, 할인·웨이팅 제보
6. 투표방(진행·결과), 투표 만들기, 회식 모드, OG·결과 공유 이미지
7. 앱 아이콘·스플래시, 관리자 화면

### 8.2 디자인 방향 [확정 + 보완]

정본은 1단계에서 확정하는 루트 `DESIGN.md`이고, 확정 전에는 `docs/design/preferences.md`를 따른다.

- **톤**: 따뜻하고 편안한 미니멀. 따뜻한 밝은 배경(크림·샌드·오프화이트) + **흙빛 계열 단일 포인트 컬러**(테라코타·올리브·캐러멜·클레이 중 디자인 시스템 시안에서 선택)
- **타이포**: Pretendard 단일 서체(예외: 시안 B에서만 제목 세리프 시도), 숫자(도보 분·가격)는 크게·`tabular-nums`
- **레이아웃**: 한 손 조작, 주요 버튼은 화면 하단 1/3, 터치 영역 44px 이상, 넓은 여백, 카드 중심
- **모션**: 강도 보통. 카드 스와이프, 다시 뽑기 셔플, 바텀시트 스프링, 득표 바·숫자 롤링, 확정 순간 짧은 축하 모션. `prefers-reduced-motion` 존중
- **다크 모드**: 라이트 우선, 다크는 따뜻한 차콜로 모든 시안에서 동등 지원, 포인트 컬러 채도 조정
- **컴포넌트**: shadcn/ui + Lucide + Motion(`motion/react`), 디자인 토큰(색·간격·라운드·그림자·모션 시간) 먼저 정의

- **피할 것**: 빽빽한 정보, 과한 그라데이션과 글래스모피즘

### 8.3 사진 없는 카드 디자인 (빠진 요구사항) [PRD 추가]

카카오 로컬 API는 **식당 사진을 제공하지 않는다**. 추천 카드가 사진 없이도 매력적이어야 한다.

- 카테고리별 **일러스트 + 색면** 시스템 (12종, 목록은 tasks.md T2.8). 음식과 그릇 중심, 마스코트·캐릭터 없음
- 카드의 **시각적 주인공은 카테고리 일러스트** [확정, preferences.md], **정보 위계의 주인공은 식당명과 숫자**(도보 약 4분, 9천 원대, 👍 87%. 카드에서는 문자 구분자 없이 간격으로 나눔)
- 일러스트 화풍은 디자인 시스템 시안에서 비교: 손맛 있는 채색(A) / 가는 선화(B) / 단정한 플랫(C)
- 사용자 업로드 사진은 MVP에서 받지 않음 (저작권·초상권·검수 부담) → 2단계 검토

### 8.4 화면별 상태 요구사항

모든 데이터 화면은 **로딩(스켈레톤) · 빈 상태 · 오류 · 오프라인** 4가지 상태 디자인을 시안에 포함한다.

## 11. 정책

### 11.1 투표 정책

basic-plan 3.2절 규칙 유지: 1인 1표(복수 선택 시 후보별 1표), 마감 전 변경 가능, 최대 30명, 마감 24시간 후 링크 만료, 방장만 후보 수정·마감, 초대 링크 보유자만 열람.

### 11.2 후기 정책

- 기본 공개, 작성 시 비공개 선택
- 공개 후기에는 닉네임·프로필 사진 노출, 방문 날짜는 "○월" 단위로만
- 비공개 후기도 가격·👍·태그는 식당 집계에 익명 포함, 텍스트만 비공개 [확정]. 가입 화면·후기 작성 화면에 이 사실을 한 줄로 고지한다.
- 신고 3건 누적 자동 숨김, 관리자 최종 판단

### 11.3 위치정보

- 현위치: 브라우저에서 추천 계산과 지도 중심 이동에만 사용, 서버·분석 도구·오류 모니터링으로 전송하지 않음. 현위치 버튼은 지도 중심만 옮기고 저장 경로와 분리한다(테스트로 보장)
- 사무실 좌표: 사용자가 지도에 직접 놓은 핀 좌표만 보관. 카카오·네이버 검색·지오코딩 결과 좌표는 저장하지 않음
- 위치기반서비스사업 신고: 현위치를 단말 안에서만 쓰는 구조는 신고 비대상이라는 것이 KISA 공개 안내다. 공개 출시 전(tasks T10.1) KISA 위치정보지원센터에 구조를 설명하고 서면 확인을 받는다. 신고 필요 회신이면 신고와 약관·동의 화면을 추가한다 (T0.18, 2026-10-28)

### 11.4 탈퇴·데이터 삭제

- 탈퇴 즉시: 프로필·사무실·설정(기피 음식·선호도 포함)·방문·즐겨찾기·다시 안 갈 곳·피드백·웨이팅 제보·폐업/정보 제보·할인 제보와 확인 응답·후기 신고 기록 삭제
- 후기: 공개·비공개 모두 삭제, 식당 집계에서도 빠짐 [확정]
- 투표 기록: 진행 중 투표의 내 표는 삭제, 확정된 투표는 익명 참여자로 남김
- 법령상 보관 의무 데이터 없음(결제 없음)

### 14.1 서비스 도메인 [확정]

- **개발 기간**: Vercel 기본 도메인(`*.vercel.app`, 예: `lunchmate.vercel.app`)을 쓴다. 0단계 외부 등록 전에 프로젝트 이름이 비어 있는지 먼저 확인하고(tasks T0.5), 모든 외부 콘솔에는 이 **프로덕션 도메인**과 `http://localhost:3000`을 정확한 주소로 등록한다. `main` 직접 푸시 체계라 PR 미리보기 도메인은 등록하지 않는다(PR 체계 전환은 tasks T9.12에서 재검토).
- **베타 시작 전(늦어도 공개 출시 전)**: 자체 도메인(예: `lunchmate.kr`)을 구매해 Vercel에 연결한다(tasks T9.2). 베타 전에 연결해야 베타 참여자의 PWA 재설치와 초대 링크 단절을 피할 수 있다.
- **도메인 전환 체크리스트**
  - [ ] Vercel: 자체 도메인 연결, `*.vercel.app` → 자체 도메인 301 리다이렉트 (기존 투표 초대 링크 유지)

  - [ ] 네이버: 지도 Client ID 서비스 URL, 네이버 로그인 서비스 URL·Callback URL (검수 재요청 여부 확인)
  - [ ] 구글 Cloud Console: OAuth 승인된 JavaScript 원본·리디렉션 URI
  - [ ] Supabase: Site URL, Redirect URLs
  - [ ] 네이버 지도 URL Scheme `appname` 값
  - [ ] OG 이미지·메타 태그·매니페스트의 절대 URL, PostHog·Sentry 도메인 설정
  - [ ] 환경변수(`NEXT_PUBLIC_SITE_URL` 등) 갱신 후 재배포, 실기기에서 로그인 3종·공유·길찾기 재확인
