### 1.2 베타 종료일 기록

`beta_feedback`은 `private.beta_settings.ended_on` 기준 **6개월 뒤** 매일 04:50(KST) 크론 `lunchmate_purge_beta_feedback`이 지운다(마이그레이션 `20261102120000_t9_4_beta_feedback.sql`). `ended_on`이 null이면 지우지 않는다. 탈퇴한 사람의 의견은 날짜와 상관없이 바로 지워진다(cascade).

G9에서 종료일이 정해지면 Supabase 대시보드 SQL 편집기에서 한 번 실행한다(마이그레이션 아님, `db:push` 대상 아님).

```sql
update private.beta_settings set ended_on = '2026-11-22';  -- 베타 마지막 날(KST). 연장하면 그 날짜
select ended_on from private.beta_settings;                -- 확인
```

- 11/22로 적으면 2027-05-23(KST) 무렵부터 그 전 의견이 지워진다. 회고(`docs/beta-retro.md`)에는 의견 원문을 옮기지 않고 요약만 남긴다.

### 2.4 참여자 기록 틀

**이름, 전화번호, 카카오톡 아이디, 닉네임은 저장소에 적지 않는다.** 누가 몇 번인지 짝은 운영자 개인 메모(저장소 밖)에만 둔다. `/admin` "베타 의견"의 "참여자 N"(익명 번호)과 이 표의 번호는 서로 다른 번호이며 짝을 맞추지 않는다.

| 번호 | 초대일 | 받은 문구 | 기기 OS | 가입 확인 | 메모(개인정보 없이) |
| --- | --- | --- | --- | --- | --- |
| 01 | 11/16 | A | iOS | [ ] | |
| 02 | 11/16 | B | Android | [ ] | |
| ... | | | | | |

- 기기 OS: iOS, Android, PC 중 본인이 말해 준 것만. 모르면 비운다.
- 가입 확인: 본인이 "시작했다"고 답했을 때만 체크. 전체 가입 수는 `/admin` "사용자" 구역의 수로 따로 본다(초대 수보다 크게 늘면 링크가 밖으로 퍼진 것, 9장).

1. 앱 나 탭 설정의 "관리자 화면" 줄 또는 `/admin`으로 들어가 **"베타 의견"** 구역을 연다.

3. 각 의견에 붙은 정보: 참여자 익명 번호, 화면 경로 틀, 앱 버전, 추천 버전(`algo_version`), 기기(아이폰, 안드로이드, 컴퓨터, 앱 안 브라우저, 홈 화면 앱). 좌표와 UA 원문은 없다.

5. 버그와 불편은 3.4로 분류해 `docs/tasks.md` T9.10 줄 또는 회고 메모에 옮긴다. 의견 원문은 저장소에 옮기지 않고 요약만 적는다(6개월 뒤 삭제 규칙과 맞추기 위해).

## 4. T9.7 인앱 브라우저 로그인 전환율

### 4.1 계산

monitoring.md 2.9 퍼널 그대로.

- 분자: `login_completed` (15분 안, 같은 익명 id)
- 분모: `login_started`, `in_app_browser = true`
- 집계: Unique users(기기), 기간은 베타 전체(11/16~종료일). Breakdown `provider`(kakao, naver, google)
- 비교: 같은 퍼널을 `in_app_browser = false`로 하나 더

SQL로 대조할 때(HogQL):

```sql
SELECT properties.provider AS provider,
       uniqIf(distinct_id, event = 'login_started') AS started,
       uniqIf(distinct_id, event = 'login_completed') AS completed
FROM events
WHERE timestamp >= toDateTime('2026-11-16 00:00:00', 'Asia/Seoul')
  AND event IN ('login_started', 'login_completed')
  AND properties.in_app_browser = true
GROUP BY provider
```

- 이 SQL은 시간 창(15분)을 보지 않으므로 퍼널 값보다 조금 높게 나올 수 있다. 판정은 퍼널 값으로 한다. `login_completed`에도 `in_app_browser`가 실리는지는 첫날 이벤트 목록에서 확인한다 [확인 필요].

### 4.2 판정 규칙

| 조건 | 결정 |
| --- | --- |
| 인앱 `login_started` 기기 **10대 미만** | **판단 보류.** 베타 연장 시 계속 모으거나, 출시 뒤 첫 2주 값으로 다시 본다. G9 문서에 "표본 부족"으로 적는다 |
| 10대 이상, 전환율 **50% 이상** | 로그인 필수 유지(PRD AUTH-04, Q2 확정안) |
| 10대 이상, 전환율 **50% 미만** | "게스트 투표" 재검토 안건을 연다(tasks T10 이후 검토). 단 아래 확인 먼저 |

- 표본이 작다. 10대 중 5대 성공(50%)의 95% 신뢰 구간은 대략 24%~76%다. 그래서 **10대 이상 + 40%~60% 사이면 "경계"로 적고**, 숫자만으로 정하지 않고 아래 두 가지를 같이 본다.
  1. 실패가 한 provider에 몰렸는지(예: 구글만 실패 → 인앱 차단 안내 문제이지 로그인 필수 자체의 문제가 아님. 안내를 고치는 쪽이 먼저)
  2. 베타 의견 중 로그인 관련 불편이 몇 건인지
- 주의: `/beta`의 인앱 주 버튼이 외부 브라우저 열기라서(D-23) 초대 링크로 들어온 사람은 대부분 `in_app_browser = false`로 로그인한다. 인앱 표본은 주로 **투표 초대 링크**에서 생긴다. 2.2 리마인더에서 투표를 권하는 이유다.
- PRD AUTH-04 배경 문단은 게스트 투표 재검토 기준을 `poll_invite_opened → poll_voted`(monitoring.md 2.6 보조 퍼널)로 적었고, tasks T9.7은 인앱 로그인 전환율이다. 문서 우선순위(tasks > PRD)에 따라 **판정은 인앱 로그인 전환율**로 하고, 초대 → 투표 전환율은 보조로 같이 적는다. PRD 문장 정리가 필요하면 사용자에게 알린다(열린 질문 2).

## 5. T9.8 추천 가중치 실험

### 5.1 왜 A/B를 하지 않나

- 20명, 평일 점심 5일이면 추천 세션은 많아야 100개 안팎이다. monitoring.md 2.11은 버전마다 200 세션 이상을 비교 기준으로 둔다. 무작위 배정 A/B는 각 군이 10명이라 차이를 읽을 수 없다.
- 그래서 **순차 비교 + 사전 등록**으로 한다. 결과는 "방향 확인"이지 통계적 결론이 아니다. G9 문서에도 그렇게 적는다.

### 5.2 진행

| 기간 | 버전 | 할 일 |
| --- | --- | --- |
| 11/16(월)~11/18(수) | v1 = `2026-11-01.1`(현재) | 그대로 운영 |
| 11/18(수) 14:00 | 판단 | 아래 "전환 조건" 중 하나라도 맞으면 v2 준비. 아니면 v1 유지하고 실험은 출시 뒤로 미룸 |

### 5.3 변경 후보 (`src/lib/reco/constants.ts` 기준)

현재 값: `WEIGHTS = { d: 0.3, p: 0.3, b: 0.15, c: 0.25, r: 0.5, w: 0.3 }`. 양의 가중치 d+p+b+c 합은 1이고, 바꿀 때도 합 1을 지킨다.

| 후보 | 바꾸는 값 | 근거 | 이럴 때 고른다 |
| --- | --- | --- | --- |
| **ㄱ. 거리 비중 올리기 (기본 추천)** | `d 0.3 → 0.4`, `c 0.25 → 0.15` | 평판 C는 후기 3건 미만이면 중립 0.5(`MIN_REVIEWS_FOR_REPUTATION = 3`)다. 20명 베타에서 한 식당에 후기가 3건 쌓이기 어려워 C는 거의 모든 후보에 같은 값이 되고, 0.25만큼 변별력이 빈다. 그 몫을 거리로 옮긴다 | 수락률이 낮고 의견에 "멀다"가 있을 때 |
| ㄴ. 상위 집중 | `SAMPLE_TOP_N 10 → 6` | 점수 상위 10곳에서 뽑는 폭을 줄여 덜 무작위로 만든다. 다양성(같은 카테고리 최대 2장)은 그대로 | 다시 뽑기 > 2회, "엉뚱한 곳이 나온다" |
| ㄷ. 반복 회피 강화 | `CATEGORY_REPEAT_STEP 0.25 → 0.35` (`CATEGORY_REPEAT_MAX 0.5` 유지) | 최근 3일 같은 종류 감점을 키운다 | "같은 종류만 나온다" |
| ㄹ. 예산 비중 올리기 | `b 0.15 → 0.2`, `c 0.25 → 0.2` | 가격 제보가 적어 추정 가격이 많다(`ESTIMATE_BUDGET_CONFIDENCE 0.5`). 효과가 작을 수 있다 | "비싸다" 의견이 많을 때 |

## 6. T9.9 할인 제보 양과 "할인 중" 필터

PRD 6.6A: "할인 중" 필터는 MVP에 넣지 않고 베타 제보 양을 보고 재검토한다. `/admin`에는 할인 구역이 없으므로 SQL 편집기(읽기만)와 PostHog로 본다.

```sql
-- 베타 기간 제보 수: 유형, 상태별
select type, status, count(*) as reports, count(distinct place_id) as places
from public.place_deals
where created_at >= '2026-11-16 00:00+09'
group by 1, 2
order by 1, 2;

-- 오늘 살아 있는 할인(필터를 켰을 때 실제로 걸리는 양)
select count(*) as active_deals, count(distinct place_id) as active_places
from public.place_deals
where status = 'active'
  and ends_on >= (now() at time zone 'Asia/Seoul')::date;

-- 확인 응답(아직 해요, 끝났어요) 수
select count(*) from public.place_deal_checks
where created_at >= '2026-11-16 00:00+09';
```

- PostHog 보조: `deal_reported`(type), `deal_viewed`(source, screen) Trends. "할인을 본 세션 수"가 수요의 신호다.
- 재검토 기준(제안): 베타 마지막 주 평일 하루 평균 **살아 있는 할인 장소 5곳 이상**이고, 베타 의견에 "할인 중만 보고 싶다"류 요청이 **3건 이상**이면 출시 뒤 과제로 "할인 중" 필터를 연다. 둘 중 하나라도 못 미치면 MVP 제외를 유지한다. 걸리는 곳이 거의 없는 필터는 빈 결과만 보여 10초 원칙을 해친다.
- 연다면 위치는 지도 필터(MAP-03)이고 홈이 아니다(3개 이하 원칙). 필터는 표시만 거르고 추천 점수에는 반영하지 않는다(제품 원칙 6). 새 UI라 시안 절차를 거친다.

### 6.1 T10.16h 메뉴 제보 지표 (베타 첫 주, 11/16~11/20)

`menuReports`는 11/03에 모든 환경에서 켰다(사용자 결정, 베타 첫날부터 쌓이게). 첫 주 금요일에 아래 두 수를 재고 표에 적는다.

- **입력률** = `menu_reported`(source=feedback) 수 ÷ `feedback_submitted`(stage=detail) 수. PostHog Trends 두 줄, 기간 11/16~11/20, 공식 A/B. 상세 "메뉴 알려주기"(source=detail)는 따로 한 줄로 본다.
- **카드 대표 메뉴 노출 비율** = `recommendation_shown`의 `menu_cards` 합 ÷ `place_ids` 개수 합. PostHog SQL 인사이트:

```sql
select sum(toInt(properties.menu_cards)) / sum(length(JSONExtractArrayRaw(properties.place_ids))) as menu_exposure
from events
where event = 'recommendation_shown'
  and timestamp >= toDateTime('2026-11-16 00:00:00', 'Asia/Seoul')
  and timestamp <  toDateTime('2026-11-21 00:00:00', 'Asia/Seoul')
  and properties.menu_cards is not null
```

- 보조(Supabase SQL 편집기, 읽기만): 제보가 쌓인 식당 수와 카드 기준(제보 2건 이상)을 넘은 식당 수.

```sql
select count(distinct place_id) as places,
       count(*) filter (where n >= 2) as card_ready_menus
from (select place_id, menu_key, count(distinct user_id) as n
      from public.menu_reports
      where created_at >= '2026-11-16 00:00+09'
      group by 1, 2) t;
```

| 날짜 | 입력률(피드백) | 상세 제보 수 | 노출 비율 | 제보 식당 수 | 판단 |
| --- | --- | --- | --- | --- | --- |
| 11/20 | | | | | |

- MENU-06(공공데이터 첫 값) 판단(제안): 노출 비율이 **20% 미만**이면 제보만으로는 카드가 비어 있다는 뜻이라 출시 뒤 과제로 MENU-06을 연다. 20% 이상이거나 입력률이 **15% 이상**이면 제보만 유지하고 베타 끝(T9.11)에 다시 본다.
- 신고와 숨김은 `/admin` "메뉴 제보" 탭에서 매일 루틴(3.1)과 함께 본다.

## 8. T9.12 Git 전략 재검토 (초안)

### 8.1 현재

- `main` 직접 푸시 = Vercel 프로덕션 배포. pre-push 훅이 lint, typecheck, test, lint:copy를 돌린다(`.githooks/pre-push`). build와 E2E는 훅에 없다.
- Supabase는 프로젝트 하나다. 프로덕션과 미리보기 배포가 **같은 DB**를 쓴다.
- 미리보기 주소는 배포마다 바뀐다. 카카오 JS 키, 네이버 지도 Client ID의 도메인 제한과 Supabase Redirect URLs에 등록되지 않은 주소에서는 지도와 로그인이 안 된다(D-22에서 Preview 고정 주소 준비를 건너뜀).

### 8.2 비교

| 항목 | A. 지금처럼 main 직접 푸시 | B. PR + 미리보기 배포 |
| --- | --- | --- |
| 속도 | 빠름. 핫픽스 몇 분 | PR 열고 미리보기 확인, 병합까지 한 단계 더 |
| 사용자 영향 | 깨진 빌드가 바로 사용자에게 감. 되돌리기는 Vercel 이전 배포로 | 실제 화면을 미리보기에서 먼저 봄 |
| 1인 개발 | 리뷰어가 없어 PR의 리뷰 이점은 작음 | 리뷰 대신 CI와 미리보기 확인이 이점 |
| DB | 같음(마이그레이션은 어느 쪽이든 프로덕션 DB에 바로 적용) | 같음. 미리보기도 프로덕션 DB를 씀 |
| 준비 비용 | 없음 | 고정 미리보기 주소를 카카오, 네이버, Supabase에 등록. GitHub Actions CI 추가 |

### 8.3 권장안

- **베타 기간(11/16~종료)에는 A 유지.** 기간 중에 방식을 바꾸면 그 자체가 위험이고, 1급 핫픽스 속도가 더 중요하다. 대신 다음을 지킨다.
  1. 점심 피크(11:00~13:30) 배포 금지, 1급만 예외
  2. UI 변경 묶음은 푸시 전 `pnpm build`(번들 예산)와 해당 E2E 한 묶음
  3. 문제가 생기면 먼저 Vercel 대시보드에서 직전 프로덕션 배포로 되돌리고(Instant Rollback, Hobby 플랜 범위 [확인 필요]) 그다음 고친다
  4. 마이그레이션은 추가만, `pnpm db:backup` 뒤 승인받고 `db:push`(D-24, CLAUDE.md 7.1)
- **G9 뒤, 공개 출시 준비(T10) 시작 때 B로 전환.** 구체 구성:
  1. 작업 브랜치 → PR → `main` 병합 시 프로덕션 배포. 본인 승인 병합 허용(리뷰어 1명 필수 규칙은 켜지 않음)
  2. GitHub 브랜치 보호: `main` 직접 푸시 금지, 필수 상태 검사 = GitHub Actions에서 lint, typecheck, test, lint:copy, build(번들 예산 포함). pre-push 훅은 빠른 사전 검사로 그대로 둠
  3. 고정 미리보기 주소: `staging` 브랜치 하나를 두고 Vercel 브랜치 별칭 주소를 카카오 JS 키 도메인, 네이버 지도 서비스 URL, Supabase Redirect URLs에 한 번 등록. PR은 `staging`에 먼저 병합해 실기기로 본 뒤 `main`으로
  4. DB 분리: 미리보기가 프로덕션 DB를 쓰는 한 스키마 변경은 미리보기에서 시험할 수 없다. T10에서 Supabase 두 번째 프로젝트(스테이징)를 만들지 정한다(무료 플랜 활성 프로젝트 수 [확인 필요], Pro 전환 T10.6과 함께 판단)
  5. CLAUDE.md 11장, 3장 명령어, `.githooks/pre-push` 머리 주석을 그때 함께 고친다

## 9. 베타 중 위험과 대응

| 위험 | 신호 | 대응 |
| --- | --- | --- |
| Supabase 무료 플랜 일시 정지 | 대시보드에 Paused, 앱 전체 로그인과 추천 실패 | 베타 중에는 매일 사용이 있어 가능성은 낮다. **베타가 끝난 뒤 사용이 끊길 때** 위험하다. 대시보드에서 Restore. 정지 기준 기간은 [확인 필요](CLAUDE.md 13장). Pro 전환은 T10.6 |
