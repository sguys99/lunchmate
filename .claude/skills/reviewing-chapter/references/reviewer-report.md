# reviewer 보고서 서식과 축별 점검 (reviewer-report)

reviewer가 쓰는 검수 보고서의 서식과, 여섯 축(C, F, U, S, L, G)을 무엇으로 어떻게 보는지 정리한 문서입니다. 심각도와 판정 규칙은 `verdict-rules.md`, 작성자 쪽 점검 항목의 세부 명령은 `writing-chapter/references/self-check.md`, 그림 점검은 `making-figures/references/qa-checklist.md`에 있어요. 여기서는 그 문서들의 ID를 가리키기만 하고 내용을 옮기지 않습니다.

## 목차

1. 보고서 뼈대
2. C 축: 완료 기준 체크
3. F 축: 기술 사실 정확성
4. U 축: PM 독자 이해도
5. S 축: 금지 기호 외 문체
6. L 축: 서술 수위
7. G 축: 그림 검수
8. 채운 보기 (발췌)

---

## 1. 보고서 뼈대

## 3. F 축: 기술 사실 정확성

작성자의 `canon` 주석과 자가 점검 보고를 믿지 않고, 원고 쪽에서 출발해 정본으로 거꾸로 찾아갑니다.

| 점검 | 방법 | 흔한 치명 | 흔한 중대 |
|---|---|---|---|
| 손계산과 예시 숫자 | 숫자 후보를 모두 뽑아(`self-check.md` 명령 C-1) 설계서 7장 정본 행과 한 줄씩 대조. 중간값과 반올림 자릿수까지 봄. 출처 claim에 있는 논문 설정값은 정본 밖 숫자로 세지 않고, 그 값으로 만든 새 계산은 셈(`verdict-rules.md` 2.3절). 예문, 날짜 차이, 말로 쓴 배수도 직접 대입(`self-check.md` C13) | 값이 다름, 반올림을 바꿔 다른 값이 됨, 조건(독립 가정 등)을 바꿔 씀 | 계산은 맞지만 정본에 없는 숫자, 다른 권 숫자에 권 표시 없음 |
| 세계관 값 | 송장, 날짜, 조항, 포인트, 도구 ID, 선반, 물체, 로봇 사양을 `scenario-hanbit.yml`과 대조(`check_canon.py`) | 값이 다름, 정본에 없는 사실을 지어냄 | |
| 출처 | `[@key]`가 `references.yml`에 있는지, 그 자리(`where`)의 claim이 문장의 숫자와 주장을 받치는지(`self-check.md` 명령 G-9), 문장이 그 출처가 말하는 범위 안인지 | 존재 확인 못 한 논문, 수치를 확정처럼 씀 | 키 누락. unverified 키는 "보고" |
| 개념 설명 | 정의, 원리 문장이 설계서 그 장 설계와 출처의 설명과 같은 방향인지. 비유가 틀리는 지점과 충돌하는 단정이 없는지 | 개념을 거꾸로 설명, 설계서 ❗ 오해와 같은 주장을 본문이 함 | 지나친 단순화로 조건이 빠짐 |
| 🔄 정보 | 버전, 날짜, 모델명이 관리표 값과 같고 기준일이 있는지 | 관리표에 없는 더 새 값을 원고에 씀 | 기준일 누락 |
| 모델명과 성능 | "현재 최고" 같은 서술, 성능 수치의 출처와 기준일, 3권 성능 주장 꼴 | 조건을 바꿔 성능을 부풀림 | 시도 수, 일반화 칸, 원격 조작 여부 누락 |
| 가정 표지 | 가정값 앞의 "가정", "가상 단가" | | 표지 누락 |

근거를 댈 수 없는 의심(예: "이 설명이 원 논문과 다른 것 같다")은 심각도를 붙이지 않고 보고서 6장 "확인 요청"에 둡니다. 확인되면 다음 회차에서 지적으로 올려요.

## 4. U 축: PM 독자 이해도

U 축은 reader 지적 분류(`verdict-rules.md` 5장)와 reviewer 자신의 점검을 합친 것입니다. reviewer 점검은 reader가 구조상 보기 어려운 장 단위 항목에 집중합니다.

| 점검 | 방법 | 흔한 중대 |
|---|---|---|
| 질문 3개의 답 | 장 도입 질문마다 답 문단과 한 장 요약 문장 번호를 찾음 | 답이 흩어져 독자가 조립해야 함, 요약에 없음 |
| 3단 설명 | 난도 지도의 상, 최상 개념마다 비유 → 그림 → 숫자가 다 있고 순서가 맞는지 | 숫자 예시 없이 수식만, 그림 참조 없이 공간 설명 |
| 비유의 한계 | 비유마다 틀리는 지점 한 줄 | 한계 문장 누락 |
| 🧭 박스 | 트레이드오프가 이 장 개념으로 설명되는지, 질문 5개를 PM이 회의에서 그대로 쓸 수 있는지 | 장에서 다루지 않은 개념에 기댄 질문 |
| 한 장 요약 | 요약 5문장만 읽고 장의 결론을 말할 수 있는지 | 새 사실이 들어감, 질문 하나가 빠짐 |
| 기준 독자 | 그 권의 기준 독자(`reader-profile.md` 1.1절)로 문장 수준이 맞는지 | P2만 아는 개발 지식을 전제 |

## 5. S 축: 금지 기호 외 문체

금지 기호, 해요체 비율, 100자 초과, 굵은 글씨 개수는 2장 자동 검사로 판정하고 여기서 다시 세지 않습니다. 남았으면 C 축 표기 행에서 중대로 셉니다. S 축은 자동 검사가 못 보는 것을 봅니다.

| 점검 | 기준 | 흔한 심각도 |
|---|---|---|
| 어미의 자리 | 정의와 원리는 습니다체, 말 걸기, 정리, 전환은 해요체(`style-rules.md` 2장). 비율이 맞아도 자리가 틀리면 지적 | 정의를 해요체로 쓰면 중대, 어색한 전환은 경미 |
| 직역투 | `reader-profile.md` 6.1절 유형 5 표 | 경미. 같은 절에 3곳 이상이면 중대 |
| 문장 리듬 | 60자 내외, 같은 꼴 문장의 연속, 접속사 남용 | 경미 |
| 표기 통일 | "파인튜닝", 3권 "액션/동작", 한영 병기 뒤 한글 통일, 숫자와 단위 | 중대 |
| 금지된 말버릇 | "쉽게 말해", "당연히", 과장 형용사 | 경미 |
| 굵은 글씨의 쓰임 | 개수가 아니라 강조 대상이 그 문단의 핵심인지 | 경미 |

## 6. L 축: 서술 수위
