# 🔄 관리표 재확인과 갱신 제안 서식 (refresh-proposal)

변화가 빠른 정보(🔄)를 다시 확인하고, 더 새로운 정보를 찾았을 때 저자에게 올리는 제안의 서식입니다. 근거는 CLAUDE.md 8장("더 새로운 정보를 찾으면 원고가 아니라 관리표 갱신을 먼저 제안한다")과 tasks.md 4.5절, 6장 ① 작업이에요.

researcher는 관리표를 직접 고치지 않습니다. 관리표 값이 원고, 그림 캡션, 정본 숫자, 다른 권 관리표의 기준이라서, 한 곳을 바꾸면 여러 곳이 함께 움직여야 하기 때문입니다. 제안을 저자가 승인하면 그때 메인 에이전트가 관리표와 딸린 파일을 한꺼번에 고칩니다.

## 목차

1. 관리표 위치와 재확인 대상
2. 재확인 절차
3. 판정 4종
4. 제안 서식
5. 채운 예시
6. 승인 뒤 바뀌는 곳 (참고)

## 1. 관리표 위치와 재확인 대상

| 권 | 관리표 | 기준 시점 칸 | 확인 기준 칸 |
|---|---|---|---|
| 1권 | `docs/design-vol1-llm.md` 9장 | "2026년 10월 현재 파악 내용" | "확인 기준" |
| 2권 | `docs/design-vol2-agent.md` 10장 | 같음 | 같음 |
| 3권 | `docs/design-vol3-physical-ai.md` 10장 | 같음 | 같음 |

- 장 리서치에서는 "위치" 칸에 그 장 절 번호가 들어 있는 행만 재확인합니다. 위치 칸이 `7.3, 7.4`처럼 여러 장에 걸치면 이 장 절이 하나라도 있으면 대상이에요. `1.5 박스`, `7.5 박스`처럼 박스 표시가 붙은 행도 포함합니다.
- 설계서 장 메타의 "🔄 비중"이 "낮음"이고 해당 행이 없으면, 보고서에 "이 장 🔄 행 없음"이라고 적고 끝냅니다. 행을 만들자는 제안은 원고에 정말 🔄 정보가 들어갈 때만 합니다.
- 장 설계의 "출처 키" 줄에 🔄가 붙은 키(예: 1권 `nvidia-h100-spec(🔄)`, "가격표 🔄")도 대상입니다. 관리표 행이 없으면 4장 서식의 `행 추가` 제안으로 올립니다.
- 두 권 관리표가 같은 사실을 다루는 행이 있습니다. 1권 9장 11.6 EU AI Act 행과 3권 10장 11.6 EU AI Act와 기계류 행은 "일치"하도록 묶여 있어요. 한쪽을 제안하면 다른 쪽도 같은 제안에 넣습니다.
- `docs/volatile.yml`(tasks.md 4.5절)이 생기면 그 파일의 항목 ID와 현재 `checked_at`을 제안서에 함께 적습니다. 아직 없으면 관리표 행을 "권 / 위치 / 항목"으로 가리킵니다. `checked_at`은 researcher가 쓰지 않고, 저자 승인 뒤 메인 에이전트가 요약표의 확인일로 채웁니다.

## 2. 재확인 절차

1. 행의 현재 값을 글자 그대로 옮겨 둡니다. 나중에 무엇이 바뀌었는지 비교할 기준이에요.
2. "확인 기준" 칸이 가리키는 곳부터 엽니다. 그 칸이 공식 출처를 이미 정해 두었으므로 다른 곳을 먼저 찾지 않습니다.
3. 현재 값의 사실마다(버전, 날짜, 수치) 그대로인지, 더 새로운 것이 있는지 봅니다. 날짜는 공식 발표일을 기준으로 하고, 보도일과 섞지 않아요.
4. 새 정보는 `sources-and-verification.md`의 우선순위와 대조 절차를 그대로 거칩니다. 2차 자료로만 확인한 새 정보는 관리표 관례대로 "(2차)" 표시를 제안 값에 붙입니다.
5. 이 행을 받치는 키가 서지 마스터(`docs/references-master.yml`)에 있으면 그 항목의 `refresh` 묶음을 채우고, 장 파일에는 키와 `claims`를 둡니다(`references-schema.md` 2.1절, 3장). `as_of`는 관리표의 현재 기준 시점 그대로 둡니다.
6. 3장 판정 가운데 하나를 고르고, 4장 서식으로 적습니다. "변화 없음"도 적어요. 언제 무엇을 확인했는지가 다음 재확인의 출발점이 되기 때문입니다.

## 3. 판정 4종

| 판정 | 뜻 | 제안 서식 |
|---|---|---|
| 변화 없음 | 확인 기준에서 현재 값이 그대로 맞음 | 요약표 한 줄(4.1절) |
| 갱신 제안 | 더 새로운 버전, 날짜, 수치가 공식 출처에 있음. 또는 현재 값의 오류를 찾음 | 제안 카드(4.2절) |
| 충돌 | 공식 출처끼리, 또는 공식 출처와 현재 값이 맞지 않는데 어느 쪽이 맞는지 정할 수 없음 | 제안 카드, 제안 값 대신 선택지 |
| 확인 실패 | 확인 기준 페이지를 열 수 없거나 해당 정보를 찾지 못함 | 요약표 한 줄과 사유 |

행 추가가 필요하면(🔄 키인데 관리표 행이 없음) "갱신 제안"으로 다루고 카드의 `현재 값`을 "행 없음"으로 적습니다.

## 4. 제안 서식

보고서(`research-report.md` 8장) 안에 둡니다. 저자가 카드 단위로 승인, 보류, 반려할 수 있게 카드마다 ID를 붙여요.

### 4.1 요약표

```markdown
| ID | 관리표 | 위치 | 항목 | 판정 | 확인일 | 근거 키 |
|---|---|---|---|---|---|---|
| R-2-7-01 | vol2 10장 | 7.3 | MCP 사양 | 변화 없음 | 2026-10-15 | mcp-spec, mcp-2026-07-28 |
| R-2-7-02 | vol2 10장 | 7.4 | A2A | 갱신 제안 | 2026-10-15 | a2a-spec |
```

- ID는 `R-{권}-{장}-{두 자리 순번}`입니다. 장 리서치가 아니라 관리표 전체 재확인(tasks.md 4.5절)이면 장 자리에 `all`을 씁니다(`R-1-all-03`).
- 근거 키가 아직 서지 마스터에 없으면 키 뒤에 `(새 키)`를 붙이고 보고서 4장 새 키 제안에도 올립니다.

### 4.2 제안 카드

갱신 제안과 충돌은 카드 하나씩 씁니다.

```markdown
#### R-2-7-02 A2A (vol2 10장, 위치 7.4)

| 칸 | 내용 |
|---|---|
| 판정 | 갱신 제안 |
| 현재 값 | (관리표 셀 원문 그대로) |
| 제안 값 | (바꿀 셀 문장 전체. 관리표 문체 그대로, 금지 기호 없이) |
| 바뀌는 부분 | (현재 값과 다른 낱말만. 예: 옛 판 이름 → 새 판 이름과 발표일) |
| 근거 | [@a2a-spec] tier 1, check matched, 2026-10-15 열람. 원문 위치: (판 목록 페이지) |
| 교차 확인 | (있으면 다른 키나 주소. 2차만 있으면 "(2차)"를 제안 값에 붙임) |
| 영향 범위 | 원고: (grep 결과 줄) / 그림: (figures.yml refresh.ledger가 이 행인 그림 ID) / 정본: (영향 받는 N ID 또는 없음) / 다른 권 관리표: (묶인 행 또는 없음) / references.yml: (서지 마스터와 장 파일의 키 추가와 수정) |
| 요청 | 승인하면 관리표 셀 교체, 기준 시점 갱신, 딸린 파일 수정 |
```

- `현재 값`과 `제안 값`은 셀 전체를 적습니다. 낱말만 적으면 승인 뒤 셀을 고치는 사람이 문맥을 다시 맞춰야 해요.
- 제안 값의 문장은 설계서 문체(습니다체, 금지 기호 없음, 날짜는 "2026년 3월 12일")를 따릅니다. 굵은 글씨는 관리표 관례대로 최신 값에만 씁니다.
- 충돌 카드는 `제안 값` 대신 `선택지` 칸에 "가: ... [@키1] / 나: ... [@키2]"를 적고, `요청`에 "저자 판단"이라고 적습니다.
- 영향 범위를 찾는 명령은 아래와 같습니다. 출력 줄을 그대로 카드에 붙여요.

```bash
# 원고와 작업 노트에서 이 항목을 언급한 줄 (낱말은 항목에 맞게)
grep -rn "A2A" vol2-agent/ch*/index.md vol3-physical-ai/ch*/index.md 2>/dev/null
# 이 관리표 행을 기준으로 삼은 그림
grep -n "ledger: \"vol2 10장 / 7.4" docs/figures.yml 2>/dev/null
# 이 키를 인용하는 장 파일과 서지 마스터 항목
grep -ln "key: a2a-spec" vol*/ch*/references.yml
grep -n "key: a2a-spec" docs/references-master.yml
```

## 5. 채운 예시

아래는 서식 시연입니다. 관리표 셀은 2권 설계서 10장에서 그대로 옮겼고, 판정은 실제 재확인 결과가 아니라 "변화가 없다고 확인한 경우"를 가정해 적었어요.

```markdown
| ID | 관리표 | 위치 | 항목 | 판정 | 확인일 | 근거 키 |
|---|---|---|---|---|---|---|
| R-2-10-01 | vol2 10장 | 10.6 | METR 작업 시간 지평 | 변화 없음 | 2026-10-15 | kwa2025metr |
```

변화 없음이라도 요약표에 남깁니다. 저자가 승인하면 메인 에이전트가 `volatile.yml`의 `checked_at`을 이 확인일로 채워요.

갱신 제안 예시의 꼴(값은 가상의 자리 표시)

```markdown
#### R-3-8-01 Figure Helix (vol3 10장, 위치 8.3)

| 칸 | 내용 |
|---|---|
| 판정 | 갱신 제안 |
| 현재 값 | 2025년 2월 Helix(System 2 7B 약 7~9 Hz, System 1 80M 200 Hz), 2026년 1월 Helix 02(전신 제어, S0 약 10M 1 kHz 추가). 이후 버전 미확인 |
| 제안 값 | (공식 발표에서 확인한 다음 버전을 덧붙인 셀 전체) |
| 바뀌는 부분 | "이후 버전 미확인" → (확인한 버전과 발표일) |
| 근거 | (새 키) tier 2, check matched, 열람일과 발표문 위치 |
| 교차 확인 | 없음(공식 발표 1건) |
| 영향 범위 | 원고: 3권 8.3절 / 그림: 3-8-1 refresh / 정본: N8-1은 Helix와 Helix 02 값이라 바꾸지 않음 / 다른 권 관리표: 없음 / references.yml: 서지 마스터에 새 키, 3권 ch08 장 파일에 claims 추가 |
| 요청 | 승인하면 관리표 셀 교체. 정본 N8-1은 그대로 두는지 확인 |
```

괄호 자리 표시는 실제 제안서에 남기지 않습니다. 채울 수 없으면 그 카드는 "확인 실패"로 내려 적어요.

## 6. 승인 뒤 바뀌는 곳 (참고)

이 목록은 researcher가 하는 일이 아니라, 카드의 "영향 범위"를 빠짐없이 채우기 위한 점검표입니다.

| 승인 뒤 바뀌는 곳 | 맡는 곳 |
|---|---|
| 관리표 셀과 기준 시점 | 메인 에이전트(저자 승인 범위 안에서) |
| `docs/volatile.yml`의 값과 `checked_at` | 메인 에이전트 |
| 묶인 다른 권 관리표 행 | 메인 에이전트 |
| 서지 마스터의 새 키와 `refresh.as_of`, 장 파일의 `claims` | researcher(다음 리서치에서) |
| 원고의 🔄 문장과 기준일 표기 | writer(writing-chapter `box-markup.md` 8장) |
| 그림 캡션의 🔄 기준일, `figures.yml` refresh | making-figures |
| 정본 숫자 | 저자 승인 뒤 설계서 7장과 `verify_examples.py` |
