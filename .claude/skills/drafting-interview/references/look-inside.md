# "현장 들여다보기" 대체 절차

저자 답이 없거나 공개가 어려운 장은 같은 주제의 공개 사례 해설로 대체하고, 제목을 "현장 노트"에서 "현장 들여다보기"로 바꿉니다(CLAUDE.md 11장, 1권 설계서 16.1절). 제목을 바꾸는 이유는 하나예요. 독자가 공개 자료 해설을 저자 경험으로 오인하지 않게 하려는 것입니다.

## 목차

1. 시작 조건
2. 주제와 사례 고르기
3. 출처가 없을 때: 출처 요청
4. 해설 서식
5. 점검표
6. 저자가 나중에 답하면
7. 실제 사례: 1권 4장

---

## 1. 시작 조건

아래 가운데 하나가 있어야 시작합니다. 모두 저자의 말이 근거예요.

| 조건 | 근거로 적을 것 |
|---|---|
| 저자가 이 장은 답하지 않겠다고 함 | 대화의 저자 문장, 날짜 |
| 저자가 공개 점검에서 `공개 불가`로 정함 | `interview.md` 공개 가능 여부 칸 |
| 저자가 대체를 직접 요청함("현장 들여다보기로 바꿔 줘") | 요청 문장, 날짜 |

답이 아직 없다는 사실만으로는 시작하지 않습니다. 이때는 상태를 `답변 대기`로 두고 "답을 기다릴지, 대체할지"를 저자에게 물어요. 기간을 정해 재촉하지도 않습니다(CLAUDE.md 2장).

## 2. 주제와 사례 고르기

1. 후보 주제가 던지는 질문을 한 문장으로 적습니다. 예: 3권 6장 "데모 영상에서 무엇을 먼저 확인해야 하나", 1권 4장 "어텐션 비유는 어디서 통하고 어디서 오해를 낳나".
2. 그 질문에 답하는 공개 자료를 고릅니다. 출처 우선순위는 CLAUDE.md 8장(원 논문, 개발사 공식 문서와 블로그, 저명한 해설 자료, 언론)을 따릅니다.
3. 같은 장 🏭 사례 박스와 같은 사례는 쓰지 않습니다. 같은 자료를 써야 하면 다른 측면(사례 박스가 결과를 다뤘다면 들여다보기는 과정이나 한계)을 다루고, 그래도 겹치면 저자에게 묻습니다. ❗ 오해 바로잡기와 같은 키를 쓸 때는 ❗가 쓴 claim과 다른 claim을 씁니다. 같은 주장을 두 박스에서 되풀이하면 장 끝이 한 이야기로 채워져요.
4. 서술 수위(CLAUDE.md 12장)를 지킵니다. 2권 보안 주제는 원리와 공개 사례만, 3권은 공개 보도 범위의 사실과 교훈만 쓰고 특정 개인을 다루지 않아요.

장별 주제 질문과 사례 방향의 예입니다. 사례 이름은 출처 확인 전이라 적지 않았습니다.

| 장 | 후보 주제 | 들여다보기 질문 | 사례 방향 |
|---|---|---|---|
| 1권 4장 | 어텐션 비유가 통한 경험과 오해를 낳은 경험 | 공개 해설과 시각화는 어텐션을 어떻게 보여 주고, 그 비유는 어디서 엇나가나 | 해설 자료와 원 논문 시각화, 어텐션 해석 연구(실제로 쓴 것은 7장) |
| 1권 2장 | 토큰 비용 예측이 빗나간 경험 | 같은 문장도 언어와 토크나이저에 따라 토큰 수가 얼마나 달라지나 | 언어별 토큰 수를 비교한 공개 연구나 개발사 문서 |
| 3권 6장 | 데모 영상에서 먼저 확인하는 세 가지 | 공개 데모 자료는 재생 속도, 시도 수, 원격 조작 여부를 어떻게 밝히거나 밝히지 않나 | 개발사가 영상과 함께 공개한 기술 보고서의 표기 방식 |

## 3. 출처가 없을 때: 출처 요청

그 장 `references.yml`에 쓸 키가 하나도 없으면 해설 본문을 쓰지 않습니다. 기억에 의존해 쓴 사례 해설은 확인되지 않은 사실을 원고에 넣는 일이기 때문이에요(CLAUDE.md 8장 "존재를 확인하지 못한 논문, 링크, 수치는 쓰지 않는다").

대신 세 가지를 합니다.

1. `index.md`의 `.box-field` 제목만 바꾸고 본문 자리에 대기 태그를 둡니다.

```markdown
::: {.box-field}
🛠 현장 들여다보기: {주제}

[출처 필요: 현장 들여다보기 공개 사례, interview.md 출처 요청 참고]
:::
```

2. `interview.md`의 "저자에게 확인할 것" 아래에 출처 요청을 적습니다.

```markdown
### 출처 요청 (researcher)

| 항목 | 값 |
|---|---|
| 장 | {권}권 {N}장 |
| 들여다보기 질문 | {2장 1번의 한 문장} |
| 찾을 자료 | {자료 종류와 확인할 내용. 예: 데모 영상과 함께 공개된 기술 보고서에서 재생 속도, 시도 수, 원격 조작 표기가 있는 부분} |
| 피할 것 | 같은 장 🏭 사례 키 {key}, 언론 단독 수치 |
| 등록 규칙 | `references.yml`에 `status: unverified`로 추가, 사람 확인 뒤 확정 |
```

3. 상태를 `대체 출처 대기`로 바꾸고 사용자에게 출처 요청을 researcher(`researching-chapter`)로 넘기자고 알립니다.

키 이름을 짐작해서 `[@key]`로 먼저 쓰지 않습니다. 없는 키는 검사에서 잡히더라도 원고에 남은 흔적이 사실처럼 보이기 때문이에요.

## 4. 해설 서식

키가 있으면 아래 서식으로 씁니다. 키가 `status: unverified`여도 쓸 수 있지만, 장 완료 전에 사람이 확인해야 합니다(`box-markup.md` 6장).

```markdown
::: {.box-field}
🛠 현장 들여다보기: {주제}

<!-- source: 공개 사례 해설(저자 답 없음, 대체 결정 YYYY-MM-DD) -->

{문단 1: 공개 자료 해설임을 밝히는 첫 문장 + 사례 소개 [@key]}

{문단 2~3: 들여다보기 질문에 대한 사례의 답 [@key]}

{마지막 문단: PM, PO가 확인할 것. 본문 절과 잇는 한 문장}
:::
```

| 항목 | 규칙 |
|---|---|
| 첫 문장 | "공개된 자료로 ○○를 들여다봅니다"처럼 해설임을 밝힘 |
| 시점 | 1인칭 금지("제가", "저는", "저희", "우리 팀"). 저자를 3인칭으로 등장시키지도 않음("저자는 ~했다" 금지) |
| 출처 | 모든 사실 문장에 `[@key]`. 키는 그 장 `references.yml`에 있는 것만 |
| 성능 주장 | "○○ 조건에서 ○회 중 ○회 성공했다고 보고됐다" 꼴, 출처에 없는 항목은 "공개되지 않음"(CLAUDE.md 8장) |
| 이름 | 회사명, 제품명, 모델명은 박스 안이므로 출처 표기대로 씀(CLAUDE.md 8장). 일반화 규칙은 저자 경험에만 적용 |
| 🔄 | 버전, 날짜, 가격이 들어가면 그 권 🔄 관리표 값만 쓰고 "🔄 기준일:" 줄을 붙임 |
| 분량 | 2~4문단(`box-markup.md` 3.4절), 0.5~1쪽(공백 포함 약 590~1,180자, `column-format.md` 3장과 같은 환산) |
| 문체 | 칼럼과 같음(`column-format.md` 4장 문체 부분). 해석과 정리는 해요체 |
| 한빛로지스 | 섞지 않음 |

## 5. 점검표

- [ ] 시작 조건(1장)의 근거가 `interview.md` 머리표 아래에 적혀 있다
- [ ] 박스 첫 줄이 `🛠 현장 들여다보기: `로 시작한다
- [ ] 첫 문단에 공개 자료 해설이라는 문장이 있다
- [ ] 1인칭 표현과 "저자는" 표현이 0개다: `grep -nE '(^|[^가-힣])(제가|저는|저희|우리 팀|우리 회사|저자는|저자가)' "$BOX"`
- [ ] 사실 문장마다 `[@key]`가 있고 모든 키가 그 장 `references.yml`에 있다
- [ ] 사실 문장마다 그 키의 claim 문구와 견줘 범위가 넓어지지 않았다(수량어 "상당 부분", "많은", 실험 대상 생략). 칼럼 자리를 `where`에 둔 claim이 없으면 researcher 요청을 `notes.md`에 적었다
- [ ] ❗ 박스와 같은 키를 쓰면 다른 claim이다
- [ ] 같은 장 🏭 사례와 사례가 겹치지 않는다
- [ ] 키가 없을 때는 본문 없이 `[출처 필요: ...]` 태그와 출처 요청만 있다
- [ ] 금지 기호 0, 문장 100자 이하
- [ ] 질문 3개가 `interview.md`에 그대로 남아 있다

키 대조 명령입니다. 박스 추출은 `generalization.md` 4장 명령을 씁니다.

```bash
R=vol3-physical-ai/ch06/references.yml
for k in $(grep -oE '\[@[A-Za-z0-9_:-]+' "$BOX" | sed 's/\[@//' | sort -u); do
  printf "%-28s %s\n" "$k" "$(grep -cE "^[[:space:]-]*(key|id):[[:space:]]*$k[[:space:]]*$" "$R")"; done
# 0이 나온 키는 references.yml에 없는 키입니다. key 필드 이름은 tasks.md 4.4절 초기화 서식이 정해지면 그에 맞춥니다
```

## 6. 저자가 나중에 답하면

저자가 들여다보기 초안 뒤에 답을 주면 B단계로 돌아갑니다. 상태를 `답변 받음`으로 바꾸고, 대체 결정 줄은 지우지 않고 "번복: 날짜"를 덧붙여요. 들여다보기에 쓴 출처 키는 `references.yml`에서 지우지 않고, 쓰이지 않게 된 키는 보고서에 적어 researcher가 정리하게 합니다.

## 7. 실제 사례: 1권 4장

1권 4장은 저자가 인터뷰에 답하지 않고 대체를 정한 첫 장입니다(2026-10-17, tasks.md 12.1절 41번). 원고 `vol1-llm/ch04/index.md`의 `.box-field`와 `notes.md` "R2 반영과 현장 들여다보기 기록"이 정본이고, 아래는 절차대로 무엇을 정했는지만 옮긴 것입니다.

| 단계 | 4장에서 한 일 |
|---|---|
| 시작 조건 | 저자 결정 문장과 날짜를 `interview.md` 머리표 아래 한 줄로 적음. 질문 3개는 그대로 둠 |
| 들여다보기 질문 | 후보 주제(통한 비유와 오해를 낳은 비유)를 "공개 해설과 시각화는 어텐션을 어떻게 보여 주고, 그 비유는 어디서 엇나가나"로 바꿈 |
| 제목 | `🛠 현장 들여다보기: 어텐션 비유와 시각화가 통하는 곳과 엇나가는 곳` |
| 문단 구성(4문단, 인용 표지 포함 약 1,000자) | ① 첫 문장 "공개된 자료로 어텐션 비유가 어디서 통하고 어디서 엇나가는지 들여다봅니다." 해설 자료와 원 논문 부록 시각화가 통하는 곳 ② 엇나가는 곳 1: 사람의 눈길로 읽기(어텐션이 글 끝 표시 [SEP]에 몰린다는 연구) ③ 엇나가는 곳 2: 판단 이유로 읽기(다른 분포로도 같은 예측이 나온다는 주장과 반론) ④ PM, PO가 확인할 것 두 가지와 4.3절 연결 한 문장 |
| 쓴 키 | `alammar2018`, `vaswani2017`, `clark2019`, `jain2019`, `wiegreffe2019`. 모두 장 `references.yml`에 이미 있던 키라 새 출처는 필요 없었음 |
| 겹침 피하기 | 🏭 사례는 검색 서비스의 BERT 적용, 들여다보기는 BERT 헤드 분석 연구라 사례가 다름. ❗ 1은 `jain2019`의 "다른 방법으로 잰 중요도와 어긋남"을, 들여다보기는 같은 키의 "다른 분포로도 같은 예측"을 씀 |
| 상태 | 해설 초안을 썼으므로 `들여다보기 초안`이 맞음(4장은 "대체"로 적고 괄호로 풀었음) |

다음 회차에 고친 것도 이 절차의 일부입니다. 초안이 claim보다 넓게 쓴 곳이 셋 있었고, 칼럼 자리를 `where`에 단 claim 5개를 `references.yml`에 더한 뒤 표현을 claim에 맞췄어요.

| 처음 쓴 표현 | 고친 표현 | 까닭 |
|---|---|---|
| 어텐션의 "상당 부분"이 [SEP]에 모인다 | "중간 층(6~10층)에서는 절반 넘게" | claim이 층 범위와 비율을 적음 |
| 정보를 어디서 많이 가져왔는지 | 가중치를 어디에 많이 두었는지 | [SEP] 예시와 맞지 않는 말 |
| 한 연구는 … 주장했습니다 | RNN에 어텐션을 붙인 모델을 실험한 한 연구는 … | claim의 실험 대상을 밝힘 |

해설을 쓰기 전에 문장마다 claim 문구를 옆에 두고 썼다면 이 회차는 필요 없었습니다. 5장 점검표의 claim 대조 항목이 그 몫이에요.
